## 一、测试覆盖率：最紧迫的技术债

**现状**：46 个 Service 文件中仅 8 个有测试（**14% 覆盖率**）。

**风险**：313 个端点中 305 个无自动化验证——每次改动只能靠人工回归。虽然 312 个现有测试质量不错（覆盖了备份、客户、需求、文档、权限等核心路径），但缺失的 86% 意味着：
- 修一个 Bug 可能引入另一个而无人发现
- 重构（如拆大文件）无法安全进行
- 新人上手无法通过测试理解业务逻辑

**建议**：
| 优先级 | 行动 | 预估 |
|---|---|---|
| P0 | 为 `documents.service`（1205行）、`quotations.service`、`projects.service` 补测试 | 3 天 |
| P1 | 为所有 controller 补 E2E 测试（用 supertest） | 5 天 |
| P1 | CI 中加入覆盖率门禁（≥50% 起步，逐步提升到 80%） | 1 天 |

## 三、AI 质量瓶颈：96% 的文档没有被解析

**现状**：456 篇文档中仅 19 篇有解析正文（**>60 字**），其余 437 篇（96%） essentially 是"死文件"——AI 问答检索不到、知识库形同虚设。

**根因**：大量文档是扫描件（营业执照、资质证明、现场照片），需要 OCR 但批量解析从未执行过。

**影响**：
- AI 问答引用命中率 0%（没有内容可引用）
- 知识库搜索返回空结果
- AI 评测集无法建立有效基线

**建议**：
| 优先级 | 行动 | 说明 |
|---|---|---|
| **P0** | 批量执行文档知识重建索引 | 系统 API 已有 `/documents/knowledge-reindex`，对 437 篇未解析文档跑一遍 |
| P0 | 开启 OCR（PaddleOCR 已内置但需确认依赖已安装） | 扫描件是主力，不开启 OCR 解析率无法提升 |
| P1 | 解析完成后重跑 AI 评测（ai-eval/run-eval.mjs） | 建立引用命中率基线 |
| P1 | 定期（如每周）自动检查未解析文档并补跑 | 避免新增文档再次积压 |

## 四、安全头缺失：Helmet 配置不生效

**现状**：curl 检查 `X-Frame-Options`、`X-Content-Type-Options`、`Strict-Transport-Security` 等安全响应头**全部缺失**——尽管代码中配置了 Helmet。

**可能原因**：
1. Helmet CSP 配置覆盖了默认安全头
2. TransformInterceptor 或全局过滤器移除了自定义头
3. Helmet 版本兼容性问题

**建议**：
| 优先级 | 行动 |
|---|---|
| **P0** | 调查 Helmet 为何未输出安全头，修复配置 |
| P0 | 手动在 main.ts 添加 `app.use(helmet({ ... }))` 并验证响应头 |

## 五、运维与部署差距

**现状**：
- ✅ 有 Docker Compose（五服务编排）
- ❌ **2,124 个文件未提交 Git**——所有改动都没有版本控制
- ❌ 无 CI/CD 实际运行（GitHub Actions 文件已写但仓库未推送）
- ❌ 无集中日志（日志只写本地文件）

- ❌ 单实例部署（无高可用）

**建议**：

## 六、性能瓶颈：并发下 P99 超标

**现状**：串行性能优秀（P99 全部 < 55ms），但并发场景下退化严重：

| 场景 | P50 | P99 | 达标(<500ms) |
|---|---|---|---|
| 5 线程并发 | 64ms | 732ms | ❌ 超标 |
| 10 线程并发 | 121ms | 858ms | ❌ 超标 |
| 20 线程并发 | 169ms | 823ms | ❌ 超标 |

**根因**：
1. 所有并发请求共享单个 Node.js 事件循环（CPU 密集操作如 Excel 导出会阻塞）
2. 无 Redis 缓存层（当前内存缓存在单实例下有效但不可扩展）
3. 数据库无读写分离

**建议**：
| 优先级 | 行动 | 预期效果 |
|---|---|---|
| P1 | Excel 导出改异步（后台任务 + 下载通知） | 消除长阻塞 |
| P1 | 引入 Redis 缓存（BullMQ 已有依赖，启用即可） | 热点数据跨实例共享 |
| P2 | Node.js Cluster 模式（利用多核） | 吞吐提升 4-8 倍 |
| P2 | PG 读写分离（主写从读） | 读密集场景并发翻倍 |

## 八、架构演进方向

**当前**：模块化单体（NestJS 单进程） + Python AI 微服务 + PG 单实例

**短期（1-3 月）**——不需要改架构：
- Redis 缓存 + BullMQ 异步任务
- Node.js Cluster 多进程
- PG 主从复制（读写分离）
- 前端 CDN（静态资源）

**中期（3-6 月）**——需要拆分：
- 文档解析服务独立（OCR/ASR 是 CPU 密集型）
- 搜索服务独立（Elasticsearch 或 MeiliSearch）
- 通知服务独立（支持多渠道推送）

**长期（6-12 月）**——按需演进：
- Kubernetes 部署（当团队超过 100 人或需要多租户时）
- 微服务化（当单模块需要独立扩缩容时）
- 多租户 SaaS（当对外销售时）
